### 0. 작업C C-2b 순수 판정층 — 행 단위 상태머신 (v3.9.0, 미배선)

`skin.js` 에 §4.3 의 건별 루프를 **판정만 하는 순수 함수**로 넣었다. DOM·네트워크·쓰기·
`chrome.*`·타이머 미접촉이고, **어디에서도 호출하지 않는다**(`cRowNext` 호출처 0건 —
[진행] 버튼은 여전히 no-op 스텁). Phase 0 통과 전에 쓰기 배선을 붙이지 않는다는 스펙
§6 을 지키면서, Phase 0 결과에 의존하지 않는 층만 먼저 고정한 것이다.

| 함수 | 역할 |
|---|---|
| `cRequeryUsable` | `fetchOrderRow` 결과가 쓰기 판정에 쓸 만한 관측인가 |
| `cCheckedSetExact` | standby 직전 "체크된 게 정확히 그 한 건인가" |
| `cClassifyStandbyOutcome` | standby dispatch 후 성공/확정실패/미확정 3분기 |
| `cCanWrite` | 쓰기 **직전** 즉시 게이트(게이트·취소·컨트롤러·계정) |
| `cIsWriteAction` | 그 action 이 네이티브 쓰기인가 |
| `cRowNext` | (단계, 관측) → (다음 단계, 다음 행동) reducer |

새로 닫은 구멍 하나: **`hasMore` 면 `found` 여도 거부**한다. 응답이 잘렸으면 같은
orderSeq 가 뒤 페이지에 또 있어도 중복을 검출하지 못한다(§4.4 "pageSize 500 은 전부의
증거가 아니다"). 종전 C-2a 는 `hasMore` 를 반환만 하고 판정에 쓰지 않았다.

`abort`(쓰기가 없었던 게 확실 → 재시작 안전)와 `halt`(미확정 → 재시도 금지)를 **이름부터
분리**했다. 사용자에게 주는 의미가 정반대인데 둘 다 "중단"으로 뭉개면 §3.6 이 무너진다.

테스트 `tests/orderitem-c2b.test.js` 43건. 2026-07-27 교훈("소스 문자열 존재 확인은 조합
버그를 못 잡는다")을 반영해 단계별 단위테스트 위에 **전 구간 시나리오 8건**을 올렸다 —
관측을 순서대로 먹여 실제로 끝까지 돌리고, 쓰기 action 이 나올 때마다 `cCanWrite` 를
통과시켜 trace 를 통째로 대조한다. 계정 전환·취소·미확정·체크집합 오염·후보 0건이
전부 "두 번째 쓰기가 안 나간다"로 떨어지는지 실행으로 확인한다.

## ⚠ 알고 미룬 것 — C-2b 에서 반드시 처리

### 1. 작업B 가 계정 전역 writer lock·저널에 참여하지 않는다

설계 §5 는 **A·B·C 전부** 계정 전역 exclusive writer lock 에 참여하라고 요구한다.
작업B 는 지금 참여하지 않는다. `skin.js` 작업B 블록 상단에 주석으로 표시해 뒀다.

**유예 근거**: 작업B 는 네이티브 수정폼을 패널로 옮긴 것이라 HTTP 쓰기 표면이 늘지 않는다
(두 탭 lost-update 는 지금 네이티브 ERP 에도 존재한다). 락의 유일한 상대는 아직 없는 C 이고,
락 API 가 C 가 도입할 job/controller 모델에 묶여 있어 지금 배선하면 B 쪽 프로토콜을 두 번
설계하게 된다.

**그래도 남는 실제 구멍**(검수가 지적했고 인정한 것): 확장이 **성공 oracle 을 새로 추가**했다.
탭1 이 A→B 로 바꿔 저장했는데 실패하고, 그 사이 탭2 가 같은 주문을 B 로 저장했다면, 탭1 의
재조회값이 B 라서 **자기 저장이 성공한 것으로 오인**한다. 최종 서버값이 사용자 의도와 같아
추가 쓰기 피해는 없지만 "이 제출이 성공했는가"는 거짓이다. **계정 전환 중 저장도 차단되지
않는다** — 이쪽이 진짜 위험이고 C-2b 의 계정 가드와 함께 닫아야 한다.

### 2. 값이 안 바뀐 `form.submit()` 이 login/other 로 착지하면 무시된다

단순 이탈과 구분할 수 없어서 생긴 트레이드오프(3차 fix 의 대가). 변경값이 없어 정합성
피해는 없고, 사용자는 다음 동작에서 로그인 화면을 만난다. 주석에 남겨 뒀다.

### 3. node 테스트로 iframe·이벤트 통합 시나리오는 못 덮는다

`epDecideLoadAction` 등 순수 판정은 전 조합 실행 테스트로 고정했지만, iframe load →
`beforeunload` → `routeOk` → `epShowMsg` 까지 이어지는 실제 이벤트 순서는 실행하지 않는다.
스펙 §7 이 "브라우저 통합 검증(node 로는 못 잡는다)"으로 이미 분리해 둔 항목 → 라이브 검증 몫.
