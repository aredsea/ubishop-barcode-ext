# 회전입고 자동화 보강 — 본사반품확인 건너뛰기 · 새 바코드 팝업 강조 (2026-09-15)

사장님 요청(2026-09-15): ① 본사반품확인이 **이미 된** 건도 회전입고 자동화가 그 다음 절차(회전입고)를 진행하게. ② 회전입고로 **새로 발급된 바코드**가 주문전표 '본사확인' 팝업의 바코드 목록에서 강조되게 — 상품입고→재고화가 하는 것과 같은 방식으로.
브레인스토밍에서 두 건 다 **A 안 + 결과 상태줄 개선**으로 확정.

## 1. 확정된 결정

| 결정 | 내용 | 근거 |
|---|---|---|
| 1단계 실패 통과 | 본사반품확인 POST 가 `msg` 에 **`가능한 상태가 아닙니다`** 를 담고 실패하면 "건너뜀"으로 표시하고 회전입고(2단계)로 진행. 그 외 실패(통신·sKey 추출 실패·다른 문구)는 지금처럼 중단 | 사장님 확인: 본사반품확인이 안 된 건을 회전입고에 넣으면 **유비샵이 거부**한다. 그래서 확장이 "이미 확인됨"과 "대상 아님"을 구분하지 않아도 잘못된 쓰기는 안 생긴다 |
| 상태 조회 안 함(B 기각) | 회전입고 전에 바코드 상태를 따로 조회하지 않는다 | 요청 1개·실측 1벌이 더 드는데 서버 거부가 같은 안전을 준다 |
| 새 바코드 출처 | **회전입고 결과 화면**(rotateItemWriteForm.do 의 회전입고장 표)에서 기존 바코드 행을 찾은 순간 같은 행의 `새바코드` 셀을 읽는다 | 2026-09-15 읽기 실측(§3). 요청 0개 추가. 내역 목록 fetch(B 안)는 완료 전 전표 줄 노출 여부가 미실측이라 기각 |
| 보관함 재사용 | 읽은 새 바코드를 재고화 보관함 `ubStockRecent`(최근 50개·7일)에 `stkRecentAdd` 로 넣는다. 팝업 강조 코드(`asgHighlightRecent`)는 손대지 않는다 | 사장님이 "재고화와 동일하게" 요청. 팝업은 보관함만 본다 |
| 회전입고장 완료는 범위 밖 | form10(회전입고장 완료)은 지금처럼 사장님이 화면에서 누른다 | 요청에 없음. 주문장과 같은 전표 구조라 자동화하면 별도 설계·검수가 필요 |
| 결과 상태줄 | `#ub-rot-st` 가 성공 여부와 무관하게 "직전: … 실행됨"만 띄우던 것을 §4 우선순위로 바꾼다 | 1단계를 건너뛴 건이 서버에서 거부됐을 때 그걸 보는 자리가 필요 |

```

       그 외                  → 중단(기존 문구)

  → init: URL msg 있으면 상태 err                                       (신규)
  → ubHighlightPending 폴링(기존)이 기존 바코드 행을 찾으면

            없으면 상태 warn "행은 찾았으나 새바코드를 못 읽음(표 구조 변경?)"
```

## 3. 실측 (2026-09-15, 읽기 전용 — MD 계정)

- 회전입고 화면 `/rotate/item/rotateItemWriteForm.do?tcode=rotate_item` 은 주문장과 같은 전표 구조: `form1`(sKey·jun·tmpShop·barcode·배수 → `rotateItemWrite.do`) · `form10`(`rotateItemJunWrite.do` 회전입고장 완료) · `form2`(재로드) · `form3`(sKey + idx 삭제).
- 회전입고장 표(`table.t_list`, 헤더 행 + 데이터 행): 헤더 `No ¦ (빈칸) ¦ 새바코드<br>새상품번호 ¦ 새매장명<br>새상품정보 ¦ 새시세(새배수) ¦ 수량 ¦ 새판매가 ¦ 예정DC ¦ 기존바코드 / 기존판매가<br>중량 (사이즈) 색상 ¦ 기존시세(기존배수) ¦ 연결번호 ¦ 수정`. 데이터 행 예: 셀2 `<span class="f_bold">2609I8</span><br>F-NF-P-WG-PA-00DU …`(첫 토큰 = 새바코드) · 셀8 `240H1B / 22,000 …`(첫 토큰 = 기존바코드) · `input[name=idx]` 값 `22198,240H1B,RH-`(seq,기존바코드,상태 — **새바코드 없음**). → `ubFindRow(기존바코드)` 가 idx 2번째 토큰으로 행을 잡고, 새바코드는 **셀에서** 읽어야 한다.
- 회전입고내역 `/jun/rotateitem/rotateItemList.do` 의 idx 는 `22198,240H1B,RH-,2609I8`(4토큰)이고 `searchBarcode` 는 **새바코드에만** 매치(기존 바코드 검색 0건). 기본 기간은 당일. 이번 설계는 쓰지 않음(B 안 기각).
- `jun=<seq>` 를 명시해 GET 한 뒤 plain GET 은 `idx 0 · jun 빈값` 그대로 — 명시 GET 은 세션 상태를 바꾸지 않는다(주문장과 동일).
- 회전입고 결과의 서버 거부는 리다이렉트 URL `msg` 로 온다고 본다(같은 Struts 패턴 — 본사반품확인·주문 취소와 동일). ⚠ 회전입고 거부 문구 자체는 미실측(쓰기라 시험 안 함) — 그래서 문구를 해석하지 않고 **그대로** 상태줄에 보여준다.

## 4. 결과 상태줄 우선순위 (`#ub-rot-st`)

1. **err** — 로드 시 `location.search` 의 `msg` 가 비어 있지 않음 → 그 문구 그대로(회전입고 거부).
2. **ok** — 폴링이 기존 바코드 행을 찾고 새바코드를 읽음 → `240H1B → 새바코드 2609I8 · 본사확인 팝업 강조 등록`.
3. **warn** — 행은 찾았는데 새바코드 셀을 못 읽음 → `행은 찾았으나 새바코드를 못 읽음(표 구조 변경?)` + 콘솔 로그.
4. **warn** — 폴링 소진(약 7.5초) 안에 행을 못 찾음 → `회전입고 결과 행을 못 찾음 — 화면 메시지 확인`.
5. **info** — 위 어느 것도 아니면 지금처럼 `직전: <바코드> → <새매장> 회전입고 실행됨`(localStorage `UB_ROTATE_LAST`).

1은 로드 즉시, 2~4는 폴링 결과로 덮어쓴다. 1이 있으면 폴링이 행을 못 찾는 게 정상이라 4로 덮어쓰지 않는다(1 유지).

## 5. 컴포넌트 (전부 `src/skin.js` §5.6)

| 이름 | 종류 | 계약 |
|---|---|---|
| `rotStep1Outcome(res)` | 순수 | `{ok:true}` → `{proceed:true, note:''}` · `{ok:false,msg}` 에 `가능한 상태가 아닙니다` 포함 → `{proceed:true, note:'본사반품확인 건너뜀(이미 확인됐거나 대상 아님)'}` · 그 외 → `{proceed:false, note: msg || '반품 신청된 건인지 확인'}` |
| `rotNewBarcodeFromCells(headerTexts, rowTexts, oldBc)` | 순수 | 헤더 텍스트(공백 정규화)가 `새바코드` 로 **시작**하는 첫 열 i → `rowTexts[i]` 첫 공백 토큰 → 대문자. `/^[0-9A-Z]{6}$/` 이고 `oldBc` 대문자와 다를 때만 반환, 아니면 `''` |

| `rotAfterRowFound(tr, oldBc)` | 부작용 | 새바코드 → `stkRecentAdd` (실패 삼킴) → 상태줄 2/3 |
| `rotSetResultStatus(text, kind)` | DOM | `#ub-rot-st` 갱신(사이드바 미렌더면 무시) |
| `rotateRun` 변경 | 기존 | 1단계 결과를 `rotStep1Outcome` 으로 판정. `proceed` 면 note 를 상태에 붙이고 진행 |
| `ubHighlightPending` 변경 | 기존(공용) | 행 발견 시 `isRotateWrite()` 면 `rotAfterRowFound`, 소진 시 `isRotateWrite()` 면 상태 4. 재고화·메인석 페이지 동작은 불변 |
| 회전입고 배선 변경 | 기존 | init 에서 URL `msg` 를 읽어 상태 1 |

## 6. 에러 처리

- 새 코드는 전부 **표시·보관함**용이다. 어떤 실패도 회전입고 제출을 막거나 되돌리지 않는다(로그 + 상태줄).
- `stkRecentAdd` 는 기존대로 읽기 실패 시 쓰지 않는다(보관함 덮어쓰기 방지).
- 1단계 통과 조건은 문구 하나뿐이다. 문구가 바뀌면 자동화가 예전처럼 **중단**되는 쪽으로 무너진다(fail-closed).
- 쓰기 경로에 새 요청은 없다. sKey 규칙(쓰기 직전 GET 과 POST 사이에 다른 GET 금지)에 닿는 변경 없음.

## 7. 테스트 (`tests/rotate-flow.test.js`, `stock-recent.test.js` 와 같은 소스 추출 하네스)

- 배선 대조(소스): `rotateRun` 이 `rotStep1Outcome` 을 쓰고 `proceed` 거짓이면 return · `ubHighlightPending` 의 행 발견 분기와 소진 분기에 `isRotateWrite()` 훅 · 회전입고 배선에 `msg` 읽기. 각 대조는 변이(훅 제거·조건 반전)로 실제로 죽는지 확인한다.
