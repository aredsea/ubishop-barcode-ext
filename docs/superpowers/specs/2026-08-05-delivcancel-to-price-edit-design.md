# 출고 확인 취소 → 판매가 수정 진입 (설계)

2026-08-05 · 대상 `src/skin.js` · 화면 `inputItemWriteForm.do`(상품입고)

## 0. 문제

매장에 배치된 제품의 **가격이 변동되면 판매가를 고쳐야 한다.** 그런데 이미 출고된 품목은
입고장에서 **수정 링크 자체가 사라져** 고칠 수 없다. 그래서 지금은 사람이 이 순서를 손으로 밟는다:

1. 매장출고전표에서 바코드로 전체기간 검색 → 해당 출고장 체크 → 삭제 (= **출고 확인 취소**)
2. 입고전표에서 바코드로 태초 기간 검색 → 입고장번호 확인
3. 상품입고에서 그 입고장을 열고 → 해당 바코드 품목을 편집 폼에 싣고 → 판매가 수정

1~3의 **준비 과정**이 반복 노동이다. 이 문서는 그 준비까지를 자동화한다.
**판매가 입력·저장은 자동화하지 않는다** — 기존 판매가를 보고 건별로 판단해 고치는 작업이라,
사람이 값을 정해야 한다.

## 0.1 실측 결과 (2026-08-05, 라이브)

추측이 세 번 빗나간 화면이라 전부 실제로 확인했다. 아래는 실측값이다.

### 매장출고전표 `/jun/delivitem/delivItemList.do?tcode=deliv_item`

- `form1` = 검색폼, **`form2` = 액션폼** — `sKey`(hidden) + `all`(전체선택) + `idx`(행별 체크박스)
- `sKey` 예: `260805132436395` — 타임스탬프 키, **GET 마다 새로 발급**된다. 빠뜨리면 서버가 처리하지 않는다.
- 페이지 전역 함수 `del(search_form, idx_form)` 의 실체:

  ```js
  var url = "/jun/delivitem/delivItemDelete.do?tcode=deliv_item" + CONST_URL;
  idx_form.action = url;
  idx_form.submit();
  ```

  즉 **체크된 `idx` + `sKey` 를 담은 form2 를 삭제 URL 로 제출**한다.
  `CONST_URL` 은 현재 검색조건 전체(reqPage·pageSize·searchBarcode·기간 등)의 쿼리스트링이다.
- `chk_key = 0` 이라 페이지 `del()` 은 confirm 을 띄운다. 우리는 `del()` 을 거치지 않으므로
  **우리 확인창을 따로 띄운다.**
- 🔴 **`idx` 값 형식** = `423961,26079J,46885,0` — **두 번째 칸이 바코드**다. 이것으로 행을 특정한다.
- 목록 열: `No / 체크 / 출고장번호 / 매입처입고일 / 출고일(확인일) / 이미지 /
  바코드상품번호·고객명 / 구분 / 매장명·상품정보 / 수량 / 상품입고가 / 멜리입고가 / 판매가 /
  연결번호 / 상태`

### 입고전표 → 입고장 (기존 `상품 재고화` 코드와 동일 경로)

- `barcodeToJunNum()` — `/jun/inputitem/inputItemList.do?tcode=input_item`,
  `searchBarcode` + 태초(2000-01-01)~오늘 → `입고장번호`
- `junNumToSeq()` — `/jun/inputitem/inputItemJunList.do?tcode=input_item_jun`,
  `searchJunNum` + `searchItemType=1` → 행 HTML 의 `view('<seq>')`
- 입고장 로드 — `form2.jun = seq` + submit (action `/input/item/inputItemWriteForm.do?tcode=input_item`).
  **POST fetch 로도 같은 HTML 을 받을 수 있다**(실측) — 화면 이동 없이 사전 확인이 가능하다.

### 입고장 품목 목록 (`inputItemWriteForm.do` 안 `table.t_list`)

- 셀 15개. 열 인덱스: `0 No · 2 바코드상품번호 · 3 구분 · 11 판매가 · 14 수정`
- 수정칸 내용: `<a href="javascript:modify('402875');"><img src="/images/com/icon_modi.gif"></a>`
- 🔴 **출고된 품목은 수정칸이 비어 있다.** 이 기능의 존재 이유다. 실측 대조:

  | 바코드 | 구분 | 출고 상태 | 수정 링크 |
  |---|---|---|---|
  | `26088Y` | 일반 | 미출고 | **있음** (`modify('402875')`) |
  | `1500CN` | 일반 | **출고됨** | 없음 |
  | `1907KR` | 일반 | **출고됨** | 없음 |
  | `26088Z` | 고객 | **출고됨** | 없음 |

  → **구분(일반/고객)은 무관하고 출고 여부가 가른다.** 처음엔 구분 때문이라고 봤다가 이 대조로
  뒤집혔다. 출고를 취소해야 수정이 열린다는 사용자의 실무 절차가 맞다.

### 0.2 아직 확인하지 못한 것

- `modify(seq)` 가 정확히 무엇을 하는지(폼 제출인지 URL 이동인지)와, 편집 폼에서 판매가 필드명이 무엇인지.
  → **구현 중 실측한다.** 설계 구조에는 영향이 없다(우리는 링크를 누르기만 하고 값은 사람이 넣는다).

## 1. 범위

**한다**: 바코드 1개를 받아 ①출고장 삭제 ②입고장 조회 ③입고장을 열고 그 바코드 품목을
편집 폼에 실어 주기까지.

**안 한다**(YAGNI):
- 판매가 입력·저장 — 사람이 값을 정한다
- 재출고 — 담당자가 인지하고 직접 한다. 안내 문구도 넣지 않는다
- 여러 바코드 일괄 처리
- 되돌리기(rollback) 실행 — 로그만 남기고 판단은 사람이 한다

## 2. 화면

`inputItemWriteForm.do`(상품입고) 사이드바의 **`상품 재고화` 섹션 바로 아래**에 같은 형식으로 넣는다.
바코드 입력칸 + 실행 버튼 + 상태 표시. 기존 재고화 섹션의 마크업·톤을 그대로 따른다.

## 3. 흐름

입력은 **바코드 1개뿐**이다.

| 단계 | 동작 | 실패 시 |
|---|---|---|
| 1 | 출고전표에서 바코드로 전체기간 검색 → 대상 행 찾기(`idx` 2번째 칸 == 바코드) | — |
| 2 | **출고 기록이 없으면 중단** — "출고 기록이 없습니다" | 중단(아무것도 안 함) |
| 3 | 여러 건이면 **가장 최근 1건만** 대상으로 삼는다 | — |
| 4 | **확인창** — 바코드·출고장번호·출고일·매장명을 보여주고 승인받는다 | 취소 시 종료 |
| 5 | 처리 로그를 **삭제 전에** 기록(write-ahead) | 기록 실패면 삭제하지 않는다 |
| 6 | 출고장 삭제 POST(`sKey` + `idx`) → 리다이렉트 `msg` 로 성공 판정 | 중단(아직 안 지워짐) |
| 7 | 바코드 → 입고장번호 → seq | 중단 + "출고장은 삭제됨" 명시 |
| 8 | 입고장 로드(페이지 이동) → 그 바코드 행의 `modify(...)` 실행 | 중단 + 현재 상태 명시 |

1~7 은 화면 이동 없이 fetch 로 처리하고, 8 만 실제 이동한다(사람이 봐야 하므로).

### 3.1 페이지 이동을 건너는 방법

8 단계는 페이지가 바뀌므로 상태를 넘겨야 한다. 기존 재고화의 `ubHlStore(barcode)` 방식을 그대로 쓴다 —
localStorage 에 바코드를 저장하고, 새로 로드된 문서의 init 이 그것을 읽어 해당 행을 찾아
`modify` 링크를 누른다.

`skin.js` 는 ISOLATED world 라 페이지 전역 함수 `modify()` 를 직접 부를 수 없다.
**실제 `<a href="javascript:modify('...')">` 엘리먼트를 클릭**해 페이지 컨텍스트에서 실행시킨다.

## 4. 실패 처리

되돌리기 어려운 지점은 **6단계(삭제)** 하나다. 그 뒤 단계가 실패하면 출고장은 이미 없다.

- 6단계 이후 어떤 실패든 **"출고장은 삭제됐다"를 반드시 문구에 포함**한다. 조용히 끝내지 않는다.
- 처리 로그에 삭제 전 출고 행 전체(출고장번호·출고일·매장명·판매가·`idx` 원본)를 남긴다 —
  되돌려야 할 때의 유일한 근거다.
- 8단계에서 **수정 링크가 여전히 없으면** 그대로 알린다. 삭제가 실제로는 반영되지 않았다는 신호다.

## 5. 검증

- 단위: `idx` 파싱(바코드 추출), 최신 1건 선택, `msg` 성공 판정, 품목 행에서 `modify` seq 추출
- 실행: 가짜 fetch 로 1~7 단계를 통째로 돌려 **삭제 POST 본문에 `sKey` 와 올바른 `idx` 가 실리는지**,
  실패 시 각 단계에서 정확히 멈추는지
- 🔴 변이 검증 필수 — 이 저장소는 정적 문자열 대조 테스트가 뚫린 전례가 있다.
  특히 "출고 기록 없으면 중단", "로그 실패면 삭제 안 함" 가드를 무력화하는 변이가 죽는지 확인한다.

## 6. 알려진 함정 (이 저장소 누적)

- `form.elements` 는 `<input type="image">` 를 제외한다. 저장 버튼류는 문서 조회 + `.form` 대조로 찾는다.
- 유비샵 마크업은 폼 중첩이 깨져 있어 **DOMParser 의 `form.elements` 가 hidden 을 놓친다.**
  fetch 한 HTML 에서 hidden 을 쓸 때는 **정규식으로 직접 추출**한다.
- 성공/실패 판정은 **리다이렉트 URL 의 `msg` 파라미터**다. 응답 본문의 `alert` 문구 스캔은 항상 오탐.
- 바코드는 검색폼에 echo 되므로 `html.includes(barcode)` 로 결과 유무를 판별하면 안 된다.
- 응답 인코딩이 UTF-8/EUC-KR 혼재 → 기존 `postDoc` 의 `�` 개수 판별 방식을 쓴다.
