# 패션 상품 재고화 — 설계 (2026-11-23)

사장님 요청(2026-11-23): 상품 재고화에서 바코드를 넣은 뒤 남은 손작업(추가설명 고치기 · 판매가 넣기 ·
주문전표 본사확인 · 재고 배정)을 한 번에 진행한다. 기존 「상품 재고화」는 그대로 두고 그 아래에
**「패션 상품 재고화」** 를 따로 만든다.

## 1. 확정된 결정 (사장님)

| 항목 | 결정 |
|---|---|
| 실행 방식 | **확인 창 → [진행] 한 번.** 확인 창까지는 읽기만, [진행] 뒤 쓰기 3단계 자동 |
| 고객 후보 | 최근 7일 주문전표 중 **같은 상품코드** · 상태 **주문완료(O--)** · 매장 FASHION |
| 추가설명 | 끝의 종류 낱말 → 상품코드 둘째 칸 첫 글자(F-**B**F→B, F-**R**F→R, F-**N**F→N). 이미 대문자 하나로 끝나면 그대로. 뒤에 `/고객명`(꼬리 `/카` 등은 뗌). 자동 채움 후 직접 수정 가능 |
| 판매가 | 🔴 **구현 중 변경(사장님 2026-11-23)**: 카페24(/카) 고객 = **유비샵 주문전표의 그 주문 주문가** · 그 외 아는 마켓 = 아틀리에 마켓 가격표에서 **API 로 들어온 칸의 할인 전 판매가**(base, 없으면 price) · 직접 입력 가격·모르는 꼬리 = 빈칸(직접 입력). 아틀리에 제품은 **이름**(공백 무시 정확일치)으로 찾는다 — code_ubishop 은 거의 비어 있다. 소비자가·판매가 둘 다 |
| 구현 | **A안 — 숨은 iframe 으로 유비샵 네이티브 폼을 채우고 네이티브 버튼을 누른다** |

예: 바코드 2502N0 · 추가설명 `Silver925물방울오팔팔찌` · 고객 `백아영4672/카` →
추가설명 `Silver925물방울오팔B/백아영4672`, 판매가 = 카페24(own) 할인 전 판매가.

## 2. 흐름

```
[바코드 입력] ─읽기─▶ ① 품목 찾기 ─▶ ② 고객 후보 ─▶ ③ 판매가 조회 ─▶ [확인 창]
                                                                    │ [진행]
                                     ④ 품목 수정 저장 ◀─────────────┘
                                     ⑤ 그 주문 본사확인
                                     ⑥ 배정 팝업에서 그 바코드 선택(→ 입고완료)
```

1. **품목 찾기(읽기)** — 기존 재고화의 `barcodeToJunNum`·`junNumToSeq` 로 입고장을 찾고, 입고장 목록에서
   그 바코드 행의 품목 seq 를 얻는다. `inputItemModifyForm.do?seq=&jun=` 을 GET 해 추가설명·상품코드·
   현재 소비자가/판매가를 읽는다. 바코드가 0건·2건 이상이면 멈춤.
2. **고객 후보(읽기)** — `orderItemList.do` 를 주문일 오늘−6일~오늘, 상품코드, 상태 주문완료로 조회.
   매장 FASHION 행만. 0건이면 "후보 없음"(진행 불가), 1건이면 미리 선택, 여러 건이면 사장님이 고른다.
3. **판매가 조회(읽기)** — 아틀리에 새 Edge 함수 `price-lookup`(§4)에 (상품코드, 마켓) 을 보낸다.
4. **품목 수정 저장(쓰기)** — 숨은 iframe 에 수정폼을 열고 추가설명·`basicSalePrice`(소비자가)·
   `salePrice`(판매가)를 넣고 네이티브 [수정하기]를 누른다. 성공 = 기존 dcm 흐름과 같은 판정
   (리다이렉트/msg). 실패면 ⑤로 가지 않는다.
5. **본사확인(쓰기)** — 그 주문 행 하나만 기존 작업C(§5.10) standby 경로로 본사확인(O-- → OS-).
6. **배정(쓰기)** — 기존 제자리 배정(2026-07-18 inplace-assign 스펙)의 배정 팝업 경로로 그 주문을 열고,
   후보 중 **방금 바코드와 정확히 같은 행**만 선택한다. 없으면 멈추고 알린다(다른 바코드 자동 선택 금지).

진행 상태는 확인 창 안에 단계별(✔/✖/진행 중)로 보인다. 중간 실패 시 거기서 멈추고
"④까지 됐음 — 본사확인부터 직접" 처럼 남은 일을 적는다. 자동 되돌리기는 하지 않는다.

## 3. 순수 함수 (DOM 무관 · 단위 테스트 대상)

- `fsSuffixMarket(customerName)` — `/카`→`own`, `/스`→`smartstore`, `/쿠`→`coupang`, `/K`→`kakao`,
  `/아`→`amonds`, `/G`·`/s`→`homeshop`, `/옥`→`gmarket`, `/에`→`ably`. `/지`(G마켓·지그재그 겹침),
  `/퀸`·`/롯`·`/H`·`/협찬`·꼬리 없음 → `null`(판매가 직접 입력). 정본은 orderimport-core `MARKETS` 접미.
- `fsCategoryLetter(productCode)` — `F-BF-…` → `B` (둘째 칸 첫 글자, 대문자 아니면 null).
- `fsComposeDesc(desc, letter, customerName)` — 기존 `/…` 꼬리 제거 → 끝 종류 낱말(팔찌·반지·목걸이·
  귀걸이·발찌·브로치·피어싱·링 등 표) 을 letter 로 치환, 이미 `[A-Z]$` 면 그대로 → `+ '/' + 이름(꼬리 뗀)`.
- `fsPickPrice(rec)` — `{base, price}` → base ?? price ?? null.

## 4. 아틀리에 `price-lookup` Edge 함수 (신규, 라이브 배포)

- 입력 `{ code_ubishop, market }`(배열 최대 20쌍). 출력 `{ code, market, base, price, at }` 또는 `not_found`.
- 매칭: `products.code_ubishop` 정확일치 → `products.code` → `app_settings.marketData.prices[code][market]`.
  골드 분리(`:14k`/`:18k`)는 품위로 고른다. **code_ubishop 이 2개 이상 제품에 걸리면 `ambiguous`**
  (메모리: code 중복 다수 — 추측 금지).
- 인증: `ledger-lookup` 과 같은 `x-ledger-key`(LEDGER_LOOKUP_KEY) · 같은 허용 출처 · verify_jwt=false.
  고객 PII 없음. 로그는 건수만.
- 배포 전 blast-radius: 새 함수라 기존 함수 무접촉, 시크릿 재사용만 확인.

## 5. 화면

- 사이드바 「상품 재고화」 아래 섹션 「패션 상품 재고화」: 바코드 입력 + [불러오기].
- 확인 창(페이지 위 패널): 품목(바코드·상품명·이미지) / 고객 후보 라디오(주문일·고객명·주문장번호) /
  추가설명 입력칸(자동값, 수정 가능) / 소비자가·판매가 입력칸(출처 표시: "카페24 할인 전 판매가") /
  [진행] · [닫기]. D102 디자인 시스템(틸 #4abcc7).
- 판매가가 비었거나 고객 미선택이면 [진행] 비활성.

## 6. 안전

- 확인 창까지 쓰기 0. [진행] 한 번 = 한 품목.
- 같은 바코드 동시 진행 잠금(storage 플래그 + 시각).
- ⑥은 바코드 정확일치 행만. 후보 목록에 없으면 멈춤.
- 실패 시 자동 되돌리기 없음(되돌리기도 쓰기라 더 위험) — 남은 단계를 사람이 한다.
- 🔴 테스트·검증에서 운영 데이터 쓰기 금지. 첫 실행은 사장님 입회 1건.
- 공개 저장소 — 테스트 픽스처에 실명·전화 금지(가명).
