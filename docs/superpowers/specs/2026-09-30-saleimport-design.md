# GS샵 판매 처리 가져오기 설계 (2026-09-30)

d102-atelier '판매 처리(판처)' 페이지가 내보낸 GS샵 xlsx(`GS샵_판매처리_<기간>.xlsx`)를 유비샵 **상품판매** 화면
(`/sale/item/saleItemWriteForm.do`) 사이드바에 올리면, 확장이 **고객 확정 → 주문 줄·바코드 매칭 → 판매 줄 등록 →
실판매가 입력 → 현금결제 → 판매하기**를 고객 단위로 대신 한다.

지금은 직원이 건마다 고객 구매정보 보기 → 주문내역에서 바코드 확인 → 상품판매에 바코드 입력 → 실판매가 입력 →
결제창 현금에 합계 입력 → 판매하기를 손으로 한다.

- 방식 **A 확정(2026-09-30 사장님)**: 주문 가져오기(`orderimport`)와 같은 fetch 어댑터 + 검토 표 + 순차 실행기.
  화면·팝업을 대신 클릭하는 방식(B)과 목록만 보여주는 방식(C)은 기각.
- 배포 채널: **SHELL**(manifest content_scripts 추가) — 적용에 브라우저 재시작 필요.
- 검수 등급: **T3**(되돌리기 어려운 라이브 쓰기 — 판매·결제).

## 2. 입력 계약과 계산

### 2.1 파일
- 첫 시트 `수수료매입상세_리스트_<기간>` (atelier 스펙 `2026-09-18-settle-gs-design.md` §D, 28열). **열은 헤더 이름으로 찾는다.**
- 사용하는 열: `주문번호` `주문유형` `상품명` `주문옵션` `수취인` `휴대전화` `수량` `협력사지급금액`(W) `할인쿠폰`(X)
  `반품유보`(Y) `딜광고`(Z) `반품유보 지급`(AA) `최종 판처금액`(AB).
- `합계` 행: Y·Z·AA 의 **입력 합계 값**(숫자)을 여기서 읽는다(행별 Y·Z·AA 는 수식이라 값이 없다).
- 데이터 행 = 헤더 다음부터 `합계` 행 전까지. 빈 행은 버린다.
- 필수 열이 없거나 `합계` 행이 없으면 **파일 거부**.

### 2.2 최종 판처금액
행 r 에 대해 (ΣW = 데이터 행 W 합, 반품 행 포함 — atelier 식과 동일):

```
Y_r  = Y합 × W_r / ΣW      Z_r = Z합 × W_r / ΣW      AA_r = AA합 × W_r / ΣW
최종_r = W_r − X_r − Y_r − Z_r + AA_r        (X 빈칸 = 0)
실판매 합계_r = round(최종_r)   — 원 단위 반올림(0.5 올림)
```
- 셀에 캐시된 계산값이 있으면(엑셀로 한 번 저장한 파일) 확장 계산과 **±1원 이내**인지 대조하고, 어긋나면 파일 거부.
- 실측 검증: `하*이3785` 행 28,395.82 → 28,396 = 사장님이 입력한 실판매가.

### 2.3 행 분류
| 분류 | 조건 | 처리 |
|---|---|---|
| 반품 | `주문유형 = 반품주문` 또는 수량 < 0 | 제외(수동 처리 필요 표시) |
| 일반 | 그 외 | 매칭 대상 |

## 3. 매칭 (검토 표 — 쓰기 0)

### 3.1 고객
1. 기대 고객명 = `수취인 + 휴대전화 숫자 뒤4 + '/G'`. 휴대전화가 비면 `수취인 + '/G'`(대부분 불일치 → 차단).
2. `POST /etc/client.do?tcode=sale_item`(`searchWordType=clientName`, 부분일치)로 검색 → 확장이 `이름 ===` 로 거른다.
   정확히 1명 → 자동. 0명·2명 이상 → **차단**.
3. 차단된 행: 표에 고객 검색창(수취인 이름을 미리 채움)과 결과 목록(고객명·휴대폰·seq). 사장님이 고르면 그 행은 그 고객으로 확정(이 세션에서만).
- 실측(2026-09-30): 17행 중 13행 자동, 4행 차단 — `이*성4691`(유비샵 `이*성 4691`), `최*순0254`(안심번호 바뀜, `최*순7951/G`로 추정), `최*순5922`(미발견), `민*금`(엑셀 번호 없음, 유비샵 `민*금2837/G`).

### 3.2 주문 줄과 바코드
고객이 확정되면 그 고객의 **주문내역**(`infoClientTradeView.do?vcode=orderitem`)과 **판매내역**(`vcode=saleitem`)을 읽는다.

- 주문 줄에서 뽑는 값: 주문일 · 바코드(6자리) · 상품번호 · 상품명 · 비고의 `정산 N` · 수량 · 주문가.
- **본품 매칭**: 판매되지 않은 주문 줄(바코드가 판매내역에 없음) 중 `정산 N` 이 다음과 같은 줄.
  - 수량 1: `정산 N = W_r`.
  - 수량 q > 1: `정산 N = W_r / q` 인 줄을 **q개**(실측: `박*주0248` 수량 2 → 정산 259,000 줄 2개, W=518,000).
  - 후보 수가 정확히 필요한 개수와 같아야 자동. 모자라거나 남으면 **차단**(사장님이 줄을 체크해 고름).
- **이미 판매됨**: `정산 N = W_r` 인 줄이 있는데 그 바코드가 판매내역에 있으면 '이미 판매됨' — 체크 불가, 건너뜀.
- **사은품**: 본품 줄과 **같은 주문일**이고 상품명에 `(사은품)` 이 들어간 판매 안 된 줄 → 같이 판매, 실판매가 0 (D2).
- 바코드가 빈 주문 줄(입고 전) → 그 행 **차단**('바코드 없음 — 입고 확인').

### 3.3 실판매가 배분
- 본품 q줄에 `실판매 합계_r` 를 균등 배분, 나누어떨어지지 않는 나머지 원은 첫 줄에.
- 사은품 줄 = 0.
- 고객 전표 현금 = 그 고객 모든 줄 실판매가 합.

### 3.4 검토 표
고객 단위로 묶어 접기/펼치기. 줄마다: GS 주문번호 · 상품명/옵션 · 고객(자동/선택) · 매칭된 바코드·유비샵 상품명 · 주문가 · 실판매가 · 판정.
- **차단(빨강, 체크 불가)**: 고객 미확정 · 주문 줄 매칭 실패(0개/과다) · 바코드 없음 · 금액 ≤ 0.
- **제외(회색)**: 반품 · 이미 판매됨.
- 체크 가능 고객은 기본 체크. 상단 요약: 처리 대상 고객 수 · 줄 수 · 현금 합계 · 차단/제외 수.

- `sKey` 는 매 쓰기 직전 GET 에서 새로 받고, 그 GET 과 POST 사이에 다른 GET 을 끼우지 않는다(주문 가져오기와 동일 규칙).

- 결제(3)는 판매하기(4) **전에** 이미 결제전표(payJun)를 만든다. 3 이후~4 이전에 실패하면 결제전표가 남는다 → **3 이후 실패는 fatal(전체 중단·보고)**, 결제 취소를 자동으로 하지 않는다.
- ⚠ **판매직원(`saleManager`)은 HTML `selected` 가 아니라 인라인 스크립트 `form1.saleManager.value = "홍해진";` 로 선택된다**(실측). 정규식 폼 추출은 첫 옵션(`--` 빈값)을 돌려주므로, 확장은 그 스크립트에서 값을 읽어 보내고 **못 읽으면 그 고객 중단**(판매직원 빈값 저장 방지).
- `dcRate` 는 화면 JS `calDcRate` 와 같은 규칙: `Math.round(dcPrice / tmpSalePrice * 10000) / 100` 을 소수 2자리 문자열로(32.39). `dcPrice = tmpSalePrice − saleDcPrice − cashPoint`.
- 결제폼은 payJun 이 이미 있으면 **등록된 현금을 payCash 에 보여 준다**(실측 75,722). 확장은 결제를 전표당 **한 번만**, payJun 빈 상태에서 보낸다 — 재시도로 두 번 보내지 않는다.
- ⚠ 사은품 줄(실판매가 0 → dcRate 100) 은 이번 실측에 없었다. 첫 라이브 실행에서 사은품 있는 고객 1명으로 확인한다.
- ⚠ Claude Code 의 자동 모드 검사가 3(현금결제)을 '실제 금전 거래'로 분류해 막았다(자사 ERP 장부 기록이며 금전 이동 아님 — 사장님 확인 후 권한 우회 모드에서 진행). **확장 런타임과는 무관**하다(확장은 사장님 브라우저에서 돈다).

### 4.2 고객 한 명의 흐름
1. **가드**: plain GET `saleItemWriteForm.do?tcode=sale_item&pageSize=20&searchSortType=seq` → tradeJun 빈값·idx 0 이 아니면 시작하지 않는다.
2. **줄 등록**(줄마다, §4.1-0·1): 고객 지정 GET(첫 줄) 또는 tradeJun 지정 GET → sKey → POST → 응답의 idx 목록에 그 바코드 행 +1, tradeJun 보관.
3. **실판매가**(줄마다, §4.1-2) → 판매폼 목록 행의 실판매가 = 기대값.
4. **최종 대조**: 판매폼 GET 의 줄 수·바코드·실판매가 합 = 검토 표.
5. **현금결제**(§4.1-3) → 응답 payJun 비어 있지 않음 + 총 결제금액 = 합계.

## 10. 마켓별 읽기 규칙 (2026-10-01 — 다른 마켓 원본 파일)

GS샵 파일은 아틀리에가 만든 것이지만, **다른 마켓은 마켓 사이트에서 받은 원본 파일**이다(사장님 2026-10-01).
마켓마다 양식이 달라 확장 안에 **마켓 규칙(어댑터)** 을 둔다. 판매 처리(§4)·미수금 0(D8)·안전장치(§6)는 공통.

### 10.1 어댑터 계약
```
{ id, label, suffix,                 // suffix = 유비샵 고객명 접미(주문 가져오기 마켓표: 'G', '카', …)
  clientRule: 'exact' | 'prefix4',   // 고객 확정 규칙(10.3)
  matchMode:  'perUnit' | 'perOrder',// 주문 줄 매칭 규칙(10.4)
  detect(header: string[]) → bool,   // 첫 시트 첫 줄 헤더로 판별
  parse(rows) → { ok, rows: Row[], error } }
Row = { r, orderNo, buyer, phone, qty|null, key, amount, isReturn, name, option }
      key = 주문 비고 `정산 N` 과 맞출 금액, amount = 최종 판처금액(원, 정수)
```
- 파일을 올리면 등록된 어댑터의 `detect` 를 차례로 돌려 **정확히 하나**가 맞아야 한다. 0개·2개 이상이면 파일 거부(사장님이 마켓을 고르게 하지 않는다).
- 검토 표 요약에 판별된 마켓 이름을 보인다. 장부 키는 `마켓id|주문번호`.

### 10.3 고객 확정
- `exact`(GS): §3.1 그대로 — `수취인+뒤4+/G` 정확일치 1명.
- `prefix4`(카페24): 고객명이 정확히 `^구매자이름\d{4}/카$` 인 고객이 **딱 1명**이고, 그 고객의 주문 줄 매칭(10.4)이 `ok` 일 때만 자동(사장님 10-01). 0명·2명 이상·매칭 실패면 **차단** → 사장님이 검색해 고른다(§3.1 과 같은 UI, 검색창에 구매자 이름).
- 같은 구매자 이름의 결제가 파일에 여러 줄이면 한 고객 묶음(D6 — 판매전표 1장).

### 10.4 주문 줄 매칭
- `perUnit`(GS): §3.2 그대로 — 판매 안 된 본품 줄 중 `정산 = key/qty` 가 **정확히 qty 개**.
- `perOrder`(카페24): 비고 정산이 **결제 전체 금액**이라 그 결제의 모든 줄에 같은 `정산 N` 이 붙는다(실측: 이다라 2줄 모두 `정산 19,807`). 그래서
  - 판매 안 된 본품 줄 중 `정산 = key` 인 줄 **전부**(1개 이상)가 그 결제의 줄이다. 0개면 차단.
  - 이미 판매된 줄만 있으면 '이미 판매됨'. 같은 고객의 두 결제가 같은 key 를 가지면 어느 줄이 어느 결제인지 모르므로 **차단**.
  - 바코드 없는 줄이 섞이면 차단(§3.2 와 같음 — 실측: 이다라 줄은 바코드 없음·`정계약 취소`).
  - **금액 배분 = 유비샵 주문가 비율**(사장님 10-01): 각 줄 `floor(amount × 주문가 / Σ주문가)`, 나머지 원은 첫 줄. Σ주문가가 0 이면 차단. 사은품(같은 주문일, 판매 안 됨)은 0원으로 같이.
  - 비고에 정산이 없는 수기 주문(실측: 배카타)은 매칭 0 → 차단(사장님이 직접 처리).

### 10.7 T3 검수로 더해진 차단 규칙 (2026-10-01 — 모두 '차단만 늘리는' 쪽)

고객 확정(10.3)
- 고객 검색 결과가 **잘렸을 수 있으면**(목록의 **전체 데이터 행** 수가 100 이상, 또는 첫 행 `No` 가 그 목록 행 수보다 큼) 자동 확정하지 않는다(GS exact 포함).
  - 4.3.5: 비교 기준은 선택 가능한 행(`setSeting` 링크)이 아니라 **목록에 보이는 모든 행**이다. 예비고객·타 매장 행은 선택 링크가 없어, 선택 가능 행만 세면 20행 목록(No 20..1)이 13행으로 읽혀 '100건 이상' 오탐이 났다(실측). 합성 픽스처 `client-search-mixed.html`(20행 중 13행 선택 가능)로 고정.
- 판정은 core `slAutoDecision` 한 곳에서 한다(패널은 결과만 쓴다).

주문 줄 매칭(10.4, perOrder)
- 판매 안 된 본품 줄이 **여러 주문일**에 걸치면 차단.
- 결제 파일 상품명의 `외N건`(없으면 N=0)으로 기대 상품 수 = N+1. N ≥ 1 이면 **줄 수가 정확히 N+1 이고 상품번호가 모두 달라야** 한다(같은 날 묶음을 두 번 산 경우 차단). N = 0 이면 상품번호가 하나여야 한다(같은 상품 여러 줄 = 수량, 허용 — 같은 날 같은 단일 상품 재주문은 구분 불가한 **수용된 한계**).
- 상품번호를 못 읽은 줄(빈 code)이 있으면 차단.
- 결제의 일부 줄만 이미 판매됐으면 차단.

공통(perUnit·perOrder)
- 주문 비고에 `취소` 가 든 줄이 후보에 섞이면 차단.
- **묶음 간 줄 겹침**: 체크 가능한 묶음끼리 같은 바코드를 잡으면 둘 다 차단(직접 고른 고객 포함). 매칭 직후와 실행 직전에 다시 검사(`slOverlaps`).
- 실행이 끝난(done) 묶음은 상태를 '완료'로 바꾸고 다시 체크할 수 없다(같은 줄 이중 판매 방지).
- 파일 판별은 어댑터가 정확히 하나일 때만(두 어댑터 헤더가 섞인 파일은 거부 — 테스트로 고정).

### 10.8 아틀리에 원장 연동 (2026-10-01 — 사장님 결정 'A: 조회 전용 API')

**원장 고객 규칙(clientRule `ledger`)**
- 파일 행마다 `ledgerNo`(원장 주문번호 — 마켓별 열은 아래 표)로 조회, `market === adapter.ledgerMarket` 인 원장 행만 쓴다.
- 고객명 = `recipient.trim() + 전화 숫자 뒤4 + '/' + suffix` — 주문 가져오기 규칙과 같다. 정확일치 1명이면 자동(§10.7 의 잘림 규칙 그대로).
- 같은 주문의 원장 행들이 서로 다른 수령자·전화면 차단('원장 수령자 불일치'). 원장 상태에 `취소` 가 있으면 차단.
- 조회가 **성공했는데** 그 주문이 원장에 없으면: 파일에 구매자 이름이 있는 어댑터(카페24·SSG)는 기존 `prefix4` 로, 없으면(쿠팡·퀸잇) 차단('원장에 없는 주문 — 직접 처리하세요', 고객 검색창 없음).
- 묶음 키는 이 고객명(원장 없으면 기존 키).

**원장 매칭(`ledgerMatch: true` — 쿠팡·퀸잇·아몬즈·에이블리)** — 원장에서 찾은 주문에만 쓴다. 🔴 **카페24·SSG 는 원장을 고객 이름 도출에만 쓰고**, 줄 매칭·금액 배분은 원래 모드 그대로다(카페24 perOrder + 주문가 비율, SSG perUnit). 아몬즈는 4.3.6 부터 원장 매칭이다(아래 어댑터 표·'4.3.6 아몬즈').
- 주문마다 기대 줄 = 원장의 **사은품이 아닌** 행들, 매칭 열쇠 = 그 행의 `amount`(= 유비샵 비고 `정산 N` — 이지어드민 정산금액. 실측: 쿠팡·퀸잇 3건 일치). 파일 금액이 아니라 원장 금액으로 줄을 찾는다(실측: 쿠팡 파일 248,448 vs 원장·비고 248,447 — 1원 반올림 차이).
- 각 기대 줄마다 판매 안 된 본품 줄 중 `settle === amount` 가 있어야 하고(다중집합으로 정확히 같은 개수), 남거나 모자라면 차단. §10.7 의 공통 차단(취소 줄·바코드 없음·묶음 간 겹침·여러 주문일)을 그대로 적용.
- **T3 3차 검수 차단 규칙(모두 '차단만 늘리는' 쪽)**
  1. 열쇠가 **있는데** 조회가 실패(타임아웃·non-2xx·JSON 오류·예외)하면 `ledgerMarket` 어댑터의 모든 행을 차단('원장 조회 실패 — 다시 시도하세요', 폴백 없음). 열쇠가 **없을 때만** 위 폴백(안내 문구 포함). '조회 성공·주문 없음' 과 '조회 실패' 를 구분한다.
  2. 원장 번호가 `^[A-Za-z0-9-]{4,40}$` 에 안 맞으면 조용히 빼지 않고 차단('원장 번호 형식 오류'), 폴백 없음.
  3. 같은 고객의 **서로 다른 두 원장 주문**이 같은 정산액이면 차단('같은 정산액 주문이 2건 — 어느 줄인지 모름'). 한 주문 안의 같은 금액은 허용.
  4. 주문별 파일 최종 금액 합 F 와 원장 비사은품 합 L 의 차이가 그 주문의 **파일 행 수(원)** 를 넘으면 차단('파일 금액 F ≠ 원장 L — 주문 일부만 정산됐을 수 있음'). 실측 248,448/248,447(1행)은 통과.
  6. 같은 구매자 이름의 한 결제는 원장에서 확인되고 다른 결제는 이름 묶음(prefix4)으로 떨어졌으면 그 구매자의 묶음을 전부(원장으로 확인된 묶음 포함) 차단('같은 구매자의 결제 일부만 원장에서 확인됨 — 직접 처리').
  - 원장 고객명과 ERP 검색 결과를 비교할 때 접미는 대소문자 무시(SSG `/s`·`/S`), 접두는 정확일치. 조회 타임아웃은 응답 본문을 다 읽은 뒤에 해제한다.
- 실판매가 = **파일의 그 주문 최종 금액 합**을 원장 amount 비율로 배분(floor, 나머지는 첫 줄). 파일 합 = 원장 합이면 줄별로 원장 금액 그대로가 된다. 사은품(원장 is_gift 또는 유비샵 `(사은품)`, 같은 주문일)은 0원.

**4.3.5 보강 — 이름 형태·전부 반품·구분 (2026-10-06, 실제 정산 파일에서 표가 거의 다 막힌 사례)**
1. **공백·ASCII 대소문자**: 원장 고객명(`ciSuffix`) 비교는 접두·접미 모두 공백을 무시하고 ASCII 대소문자를 무시한다(한글·숫자는 정확일치). **검색 순서**(원장 묶음·폴백 수령자 검색 공통, `slSearchMerged`): 두 형태(원본 이름·공백을 모두 뺀 `slSearchWord`)가 다르면 **항상 둘 다** 검색해 seq 로 합치고 판단(정확·폴백 모두)은 합친 집합으로 한다 — 한쪽에서 후보 1명이 나왔다고 일찍 끝내지 않는다(다른 형태로 등록된 동명이인을 놓치지 않게). 첫 검색이 잘렸으면 그대로 잘림(차단)이고 둘째는 하지 않는다. 합친 뒤 잘림 표시는 둘의 OR. ubishop 검색은 부분 일치이고 공백을 무시하지 않는다(실측: 'Ann Lee' 는 못 찾고 'AnnLee' 는 고객을 찾음) — 그래서 두 형태가 다 필요하다. 원장이 아닌 exact(GS 등)와 prefix4 는 원본 키 그대로 검색한다.
2. **다른 이름 형태로 등록된 고객 — 폴백**: **원장 출처 항목(`source === '원장'`)만**, 정확 이름 후보가 0명이고 검색이 잘리지 않았을 때, 수령자 이름(공백 제거)으로 다시 검색한다. 후보 = 정규화한 이름이 `^수령자\d{4}(/.*)?$`(대소문자·공백 무시)인 행 — '수령자/타인' 같은 매장 행은 제외. 후보는 **최대 5명**(초과는 '후보가 너무 많음 — 직접 고르세요' 로 차단, 목록은 직접 고르기에 채워 둔다). 후보마다 기존 읽기 경로(고객 열기 → 미수금 0 → 주문·판매내역 → 같은 매칭 모드)를 **순차**로 돌린다. 점검 결과는 `ok`·`none`·그 밖(`block`·`sold`)이다 — **`none` = 주문내역을 읽었고 이 묶음이 필요로 하는 정산액 줄이 하나도 없음**(`slProbeNone`; 필요한 금액을 알 수 없으면 `none` 이 아니다). **자동 확정은 `ok` 가 정확히 1명이고 나머지가 전부 `none` 일 때만**이다(근거 '주문 확인'; 선택 후보로 한 번 더 읽어 반영·겹침 검사 — 이 재확인이 'ok' 로 끝나지 않거나 던지면 자동 확정을 취소하고 `client`·`how` 를 비우며 후보 목록은 직접 고르기에 남긴다). 다른 후보가 점검 불가(미수금·고객 지정 실패)이거나 근거(`sold`)·차단(바코드 없는 줄 등)이 있으면 그 후보가 진짜 고객일 수 있으므로 자동하지 않고 차단(사유에 후보별 결과, 직접 고르기 가능). 0명·2명 이상도 차단. 자동으로 고른 항목은 '직접 선택' 이 아니라 경고색 칩 '자동 · 주문 확인(이름 다름)' 으로 보인다(`slHowChip`).
   - **수용한 잔여 위험(사장님 2026-10-06 — '주문으로 입증되면 자동')**: 수령자 이름 앞부분이 같고 뒤 4자리 꼴도 같은 동명이인에게 **우연히 같은 정산액·날짜의 미판매 주문**이 있고 진짜 고객은 `none` 으로 읽히는 경우는 자동으로 잡힐 수 있다. 이런 항목은 화면의 '자동 · 주문 확인(이름 다름)' 칩으로 드러나므로 실행 전 눈으로 거를 수 있다. 읽기는 `enqueue` 안에서만 하고 판매가 시작되면 중단한다. 순수 부분: `slFallbackCandidates`·`slFallbackDecide`·`slFallbackResolve`. 쓰기 경로는 건드리지 않는다.
3. **전부 반품**: **판매 행은 절대 판매 대상에서 빼지 않는다**(빼면 같은 결제 중복 정산 방어 — `matchPerOrder` 의 seen·`SPLIT_BUYER` — 가 사라진다: 이니시스 A001 +49,000 / A001 −49,000 / B002 +49,000 에 ERP 줄 2개면 둘 다 팔리고, 쿠팡은 한 주문의 다른 옵션이 서로 상쇄될 수 있다). `slClassifyRows` 는 이름표만 붙인다 — **같은 주문번호(`orderNo` 정확일치, 원장 번호만 같은 것은 아님)**에 판매 행이 있고 그 판매 금액 합 + 반품 금액 합 = 0(배송비·조정 제외)인 반품 행은 수동 목록의 구분 '전부 반품'·비고 '판매 행도 차단됨 — 유비샵 주문은 직접 정리' 로 올린다. 그 판매 행이 든 묶음은 종전처럼 차단되며, 그 원장 주문의 판매 행이 있는 모든 주문번호가 자기 반품과 짝지어 합 0 이면(위 이름표와 같은 규칙 — 다른 옵션끼리 합만 0 인 것은 제외) 차단 사유가 '전부 반품된 주문 — 판매 안 함(유비샵 주문은 직접 정리)' 이고(`retFull`), 아니면 종전 '같은 주문에 반품·제외 행이 있음'. 부분 반품(합 ≠ 0)은 종전대로.
   - **묶음 차단 (R3, 모든 마켓)**: 전부 반품 판정은 코어 한 곳 `slFullReturnSet(rows)`(같은 `orderNo` 의 판매·반품 행이 모두 있고 금액 합 0, 배송비·조정·`time-`·`ledgerBlock` 제외)이 정하고, 이름표(`slClassifyRows`)와 묶음 차단이 같은 집합을 쓴다. 묶음(`slGroupByClient`·`slGroupLedger`, 이니시스 perOrder·원장 출처 묶음·SSG·스마트스토어·아몬즈·GS·쿠팡·퀸잇·에이블리 모두)에 그 `orderNo` 의 판매 행이 하나라도 있으면 묶음은 `pickable: false`(직접 고르기로도 ok 가 되지 않는다)로 차단되고, 사유는 묶음의 판매 주문번호가 전부 반품이면 `'<주문번호>: 전부 반품된 주문 — 판매 안 함(유비샵 주문은 직접 정리)'`, 같은 묶음에 판매해야 할 다른 주문이 섞여 있으면 `'<전부 반품 주문번호>: 전부 반품 — 같은 묶음의 다른 주문(<다른 주문번호>)은 판매해야 할 수 있음 — 직접 처리'`(묶음 전체에 '판매 안 함' 을 붙이지 않는다 · 번호는 3개까지 나열하고 '외 N건'). 행은 빼지 않는다(`seen`·`SPLIT_BUYER` 방어 유지). 다른 사유로 이미 차단된 묶음은 그 사유를 둔다. 서로 다른 `orderNo`(다른 옵션)끼리의 상쇄는 이 규칙에 걸리지 않는다. 기존 원장 줄 매칭(`slMatchLedger`)의 같은 사유는 그대로 둔다.
4. **구분**: 수동 목록('수동 처리 필요')에 **구분** 열을 둔다 — 반품 / 배송비(상품명에 '배송비'·'배송료') / 조정(에이블리 조정 사유) / 전부 반품. 스마트스토어 `구분` 이 '상품주문' 이 아닌 행과 퀸잇 `거래유형` 이 '상품 구매' 가 아닌 행은 반품이 아니므로 **파서가 남긴 자기 구분값(`kindHint`)** 을 그대로 보인다(이름에 배송비면 배송비). 판매 대상 행은 바뀌지 않는다(3번은 이름표만).
5. **전부 반품 이름표의 범위**: 합산은 확실한 원장 주문번호에만 한다 — `time-` 자리표 번호(에이블리 시각 연결 실패)와 `ledgerBlock` 이 붙은 행은 서로 다른 결제가 한 번호를 공유할 수 있어 제외한다. 검색 잘림 판정은 선택 가능한 행이 나온 **같은 `t_list` 표 안**(닫는 `</table>` 까지)의 행만 세고, 선택 가능 행 100건 이상·선택 가능 행이 목록 행보다 많음·첫 No 가 목록 행 수보다 큼도 잘림으로 본다.
6. **빈 화면**: 파일은 읽혔는데 판매 가능 행이 0이면 파일명·마켓을 보이고 '판매할 행이 없습니다 — 아래 수동 처리 목록만 있습니다' 를 낸다.

### 10.9 에이블리 정산세부내역 — 원장 시각 조회 (2026-10-01)

| id | 파일 | 판별 헤더 | 처리 행 | 제외·반품 | 최종 금액 | 원장 연결 | suffix | 매칭 |
|---|---|---|---|---|---|---|---|---|
| `ably-settle` | `*_에이블리_*_정산세부내역.csv`(UTF-8 BOM) | `상품 주문 번호`·`결제 완료일`·`정산금`·`플랫폼 수수료` | 정산금 > 0 | 정산금 ≤ 0 → 반품(수동 목록) | **정산금 그대로**(사장님 10-01: "실판매는 당연히 에이블리 엑셀 기준") | 결제 시각 → 원장 시각 조회 | 에 | ledger(쿠팡·퀸잇과 같음) |

- 파일에 원장 주문번호가 없다(파일 `상품 주문 번호` 9자리 ≠ 원장 `주문번호` 13자리). 원장 에이블리 주문번호는 **주문 시각(ms)** 이다(실측: `1785476140397` = 2026-07-31 14:35:40 KST, 파일 결제 완료일 14:35:50 — 10초 차이).
- API: `ledger-lookup` 시각 모드 `{"market":"에이블리","times":[ms,…]}` — 시각마다 ±60초 안의 원장 행(최대 100개, 촘촘한 요청 거부 `times_too_dense`). `결제 완료일`(`YYYY-MM-DD HH:mm:ss`, KST)을 ms 로 바꿔 보낸다. 같은 결제 완료일이 여러 행이면 한 시각으로 보낸다(서버도 중복 제거).
- 행 → 원장 주문: 창 안의 원장 주문(서로 다른 order_no)이 **정확히 1개**일 때만 그 주문. 0개 → '원장에 없는 주문 — 직접 처리하세요', 2개 이상 → '결제 시각이 가까운 주문이 여러 건 — 직접 처리'. 같은 결제 시각의 파일 행들은 같은 주문의 상품들이다.
- 금액: 원장 금액(이지어드민 정산금액 = 유비샵 비고 `정산 N`)으로 줄을 찾고, 실판매가는 파일 `정산금`. ⚠ **에이블리는 파일 정산금과 원장 금액의 기준이 다르다**(실측 34,848 vs 37,324 — 결제수수료·플랫폼수수료·프로모션지원금 반영 차이). 그래서 §10.8 의 '|F−L| ≤ 행 수' 대조 대신 **행 수 대조**(그 주문의 파일 행 수 = 원장 본품 행 수)로 부분 정산을 막는다(어댑터 플래그 `ledgerAmountCheck: 'count'`). 금액 배분은 원장 금액 비율(§10.8 과 같음).
- 고객명 = 원장 수령자 + 전화 뒤4 + `/에`(실측 고객 존재·비고 `정산 37,324` 일치).
- **연결 보강(T3 검수 반영, 전부 fail-closed 차단)**
  1. 한쪽 창: 주문은 결제보다 먼저 만들어지므로 `결제 − 60초 ≤ 원장 주문 시각 ≤ 결제 + 5초` 만 연결한다(결제보다 뒤에 만든 주문은 연결 안 함). '정확히 1개 주문' 모호성 규칙은 그대로.
  2. 결제 혼입: 한 원장 주문에 연결된 파일 행의 결제 시각이 둘 이상이거나 `상품 주문 번호` 가 겹치면 그 행들 전부 '서로 다른 결제가 한 원장 주문에 연결됨 — 직접 처리'. (한 결제의 서로 다른 두 상품 = 같은 결제 시각·다른 상품 주문 번호는 정상.)
  3. 금액 범위: 파일에서 `결제 금액`·`프로모션 지원금` 도 읽어, 연결된 주문마다 Σ정산금 ≤ L ≤ Σ(결제 금액 + 프로모션 지원금) (L = 원장 본품 금액 합, 사은품 제외)이어야 한다. 아니면 '원장 금액이 결제 금액과 맞지 않음 — 직접 처리'. 실측 통과 예: 정산금 34,848 · 결제 36,000 · 지원 2,000 · 원장 37,324.
  4. `조정 사유` 가 비어 있지 않은 행은 판매 행이 아니라 수동 목록(반품과 같은 취급) — 그 형태가 실측되기 전까지.
- **수용한 잔여 위험**: 상품 1개짜리 주문, 또는 같은 초에 결제된 서로 다른 결제의 여러 행이 다른 고객의 원장 주문에 붙을 가능성은 남는다 — 그 주문도 한쪽 창(−60초~+5초)과 금액 범위(Σ정산금 ≤ L ≤ Σ결제+지원)를 동시에 통과하고, 같은 창 안에 다른 주문이 없을 때만이다. 검수 프로브 C(지연 결제가 창 안의 남의 주문에 연결)·G(결제 뒤에 만든 주문에 연결)는 이제 차단된다.
